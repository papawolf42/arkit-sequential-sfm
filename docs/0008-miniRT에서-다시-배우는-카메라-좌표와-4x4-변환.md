# 0008 — miniRT에서 다시 배우는 카메라 좌표와 4×4 변환

## 0. 이 문서의 목표와 읽는 방법

목표는 행렬 공식을 외우는 것이 아니라, `transforms.json`에서 카메라 위치를 왜 마지막 열에서 읽는지 설명할 수 있게 되는 것이다.

예전에 구현한 miniRT의 실제 코드를 확인하고, 그때의 `origin`, `mat_c2w`, 광선을 지금의 ARKit 데이터와 연결한다. 우선 1~6절까지만 읽어도 다음 작은 구현을 이해할 수 있다. 7절 이후는 기억을 되살릴 때 참고하면 된다.

이번 문서는 설명과 계산 확인이다. 카메라 위치 출력 기능은 아직 구현하지 않았다. 기존 서버와 촬영 원본도 변경하지 않았다.

### 확인한 것과 아직 확인하지 않은 것

- 확인: GitHub `master`의 아래 miniRT 파일 내용을 읽었다. 프로젝트 전체를 빌드하거나 렌더 결과를 검증한 것은 아니다.
- 확인: 현재 capture JSON의 좌표계 선언과 첫 프레임 행렬을 읽었다.
- 확인: 문서의 예제 행렬과 실제 첫 프레임 계산을 현재 프로젝트의 NumPy로 실행했다.
- 미검증: 예전 miniRT의 회전 기저 저장·곱셈 관례가 현재 JSON과 모든 방향에서 일치하는지는 검증하지 않았다. 이름이 비슷하다고 배열을 그대로 복사하면 안 된다.
- 미검증: ARKit 자세가 실제 사진 대응점과 맞는지는 아직 검사하지 않았다. 자세 값이 있다는 것과 기하적으로 정확하다는 것은 다르다.

## 1. 예전에 이미 구현했던 개념

사용자 저장소: [02_miniRT](https://github.com/papawolf42/42Seoul-42Cursus/tree/master/02_miniRT)

### 1.1 카메라에는 위치와 방향이 있었다

[include/struct.h](https://github.com/papawolf42/42Seoul-42Cursus/blob/master/02_miniRT/include/struct.h)의 `s_camera`에는 다음 필드가 있다.

```c
struct s_camera
{
    t_point3 origin;
    t_vec3   normal;
    double   fov;
    t_mat44  mat_c2w;
};
```

- `origin`: 카메라가 있는 위치.
- `normal`: 카메라를 향하게 할 방향 입력.
- `fov`: 화면에 담기는 각도와 관련된 값. 파서에서는 입력 각도를 변환해 저장한다.
- `mat_c2w`: 카메라 기준의 값을 월드 기준으로 옮기기 위한 변환. `c2w`는 camera-to-world의 약자다.

지금의 ARKit JSON은 이와 비슷한 역할의 정보를 `transform_matrix`에 이미 담아서 준다. 우리가 먼저 할 일은 행렬을 새로 만드는 것이 아니라 **이미 주어진 행렬을 읽는 것**이다.

### 1.2 광선의 시작점을 이동 성분에서 읽었다

[src/hit/ft_ray_init.c](https://github.com/papawolf42/42Seoul-42Cursus/blob/master/02_miniRT/src/hit/ft_ray_init.c)의 실제 코드:

```c
ray.org = cam->mat_c2w.trans;
ray.dir = ft_vminus(ft_linear_transform(cam->mat_c2w, screen), ray.org);
```

첫 줄에서 광선의 시작점을 `mat_c2w.trans`로 설정했다. 이 문서에서 하려는 “카메라의 월드 위치 꺼내기”와 연결되는 부분이다.

두 번째 줄은 카메라 기준 화면 점을 변환한 다음, 광선 시작점을 빼서 방향을 만든다. 왜 빼는지는 5절에서 설명한다.

## 2. 좌표는 위치 자체가 아니라 ‘어느 기준에서 적은 숫자’다

방 한가운데 바닥에 원점을 정했다고 생각하자. 이것이 월드 좌표계다.

카메라는 방 안을 돌아다닌다. 카메라에도 자신의 원점과 좌우·위아래·앞뒤 축이 있다. 이것이 카메라 좌표계다.

같은 의자라도 다음 두 질문의 답은 다르다.

- 월드 좌표: 방의 원점에서 의자가 어디에 있는가?
- 카메라 좌표: 지금 카메라에서 보았을 때 의자가 어디에 있는가?

카메라를 움직여도 고정된 의자의 월드 좌표는 변하지 않는다. 하지만 카메라 기준 의자의 좌표는 바뀐다.

반대로 카메라 자신의 위치는:

- 카메라 좌표계에서는 언제나 `(0, 0, 0)`.
- 월드 좌표계에서는 카메라를 움직이면 변한다.

여기서 ‘월드’는 GPS나 지구 전체를 의미하지 않는다. 이번 capture에서는 ARKit 세션이 잡은 공간 기준이다. 이동 값은 ARKit의 미터 척도를 따르지만, 측정 오차나 누적 오차까지 없다는 뜻은 아니다.

## 3. 회전과 이동을 먼저 따로 생각하기

카메라 기준 점을 월드 기준 점으로 옮기는 식은 다음과 같다.

```text
p_world = R × p_camera + t
```

기호의 뜻:

- `p_camera`: 카메라 좌표로 적은 점. 숫자 3개.
- `R`: 카메라 축이 월드에서 어느 방향인지 나타내는 3×3 회전 행렬.
- `t`: 월드에서 카메라 원점이 있는 위치. 숫자 3개.
- `p_world`: 변환 후 월드 좌표로 적은 같은 점.

순서는 “카메라 축 방향에 맞게 회전하고, 카메라가 있는 위치만큼 이동한다”이다.

### 3.1 회전이 없는 가장 쉬운 예

카메라가 월드의 `(10, 2, 3)`에 있고, 카메라 축과 월드 축이 같은 방향이라고 하자.

카메라 기준 `(1, 0, 0)`인 점은 월드에서는 `(11, 2, 3)`이다. 카메라 위치에서 x 방향으로 한 칸 간 점이기 때문이다.

이때 `R`은 값을 바꾸지 않는 단위행렬이고, `t = (10, 2, 3)`이다.

### 3.2 회전까지 있는 예

설명용으로 다음 행렬을 쓰자. 실제 capture 행렬과는 별개의 작은 예제다.

```text
R = [ 0 -1  0 ]       t = [ 10 ]
    [ 1  0  0 ]           [  2 ]
    [ 0  0  1 ]           [  3 ]
```

이 회전은 카메라 기준 x 방향 `(1, 0, 0)`을 월드의 y 방향 `(0, 1, 0)`으로 보낸다.

따라서 카메라 기준 점 `(1, 0, 0)`은:

```text
회전 후: (0, 1, 0)
이동 후: (10, 3, 3)
```

카메라 기준의 ‘오른쪽’이 월드의 x 방향일 필요는 없다는 것이 핵심이다.

## 4. 왜 3차원인데 4×4 행렬을 쓰는가?

3×3 행렬 곱만으로는 원점을 다른 위치로 이동시킬 수 없다.

```text
어떤 3×3 행렬 × (0, 0, 0) = (0, 0, 0)
```

그런데 카메라 원점을 월드의 카메라 위치로 옮기려면 이동이 필요하다. 그래서 회전과 이동을 한 번의 행렬 곱으로 표현할 수 있도록 성분을 하나 추가한다. 이를 **동차좌표**라고 한다.

지금 필요한 규칙은 다음 두 개다.

```text
점:   (x, y, z) → (x, y, z, 1)
방향: (x, y, z) → (x, y, z, 0)
```

여기서 마지막 성분은 새로운 공간 축이 아니다. 이번 강체 변환에서 이동을 적용할지 구분하는 역할로 이해하면 된다. 일반적인 동차좌표와 원근 투영은 더 넓은 개념이지만 지금은 필요하지 않다.

회전과 이동을 합친 행렬은 이렇게 생겼다.

```text
T = [ r00 r01 r02 tx ]
    [ r10 r11 r12 ty ]
    [ r20 r21 r22 tz ]
    [   0   0   0  1 ]
```

이 문서는 열벡터를 오른쪽에 놓고 `T × p`로 곱하는 관례를 사용한다.

한 행과 벡터를 곱할 때는 같은 자리에 있는 값끼리 곱해서 더한다. 첫 번째 결과는:

```text
x_world = r00*x + r01*y + r02*z + tx*1
```

나머지 행도 같은 방식이다. 결과적으로 앞에서 본 `R × p + t`와 같은 계산이 된다.

예제 전체를 쓰면:

```text
[ 0 -1 0 10 ]   [ 1 ]   [ 10 ]
[ 1  0 0  2 ] × [ 0 ] = [  3 ]
[ 0  0 1  3 ]   [ 0 ]   [  3 ]
[ 0  0 0  1 ]   [ 1 ]   [  1 ]
```

실제로 NumPy로 계산한 결과도 `[10, 3, 3, 1]`이었다.

## 5. 점은 이동하지만 방향은 이동하지 않는다

카메라를 방의 반대쪽으로 옮겨도, 회전하지 않았다면 카메라가 보는 방향 자체는 그대로다. 위치와 방향은 다른 종류의 값이다.

위의 예제 행렬에 방향 `(1, 0, 0, 0)`을 곱하면:

```text
[ 0 -1 0 10 ]   [ 1 ]   [ 0 ]
[ 1  0 0  2 ] × [ 0 ] = [ 1 ]
[ 0  0 1  3 ]   [ 0 ]   [ 0 ]
[ 0  0 0  1 ]   [ 0 ]   [ 0 ]
```

이동 값에는 0이 곱해져 사라진다. 회전만 적용된다.

### miniRT 코드와 연결

`ft_ray_init()`의 흐름을 식으로 쓰면 다음과 같다.

```text
화면 점의 월드 위치 = R × screen + t
광선 시작점        = t
광선 방향          = (R × screen + t) - t
                   = R × screen
```

즉, 점을 옮긴 뒤 카메라 위치를 빼는 방식으로 이동 성분을 없애고 방향을 얻었다. 여기서 광선 방향은 반드시 길이 1이라는 뜻은 아니다. 정규화 여부는 별도의 문제다.

[src/matrix/matrix.c](https://github.com/papawolf42/42Seoul-42Cursus/blob/master/02_miniRT/src/matrix/matrix.c)에도 두 함수가 따로 있다.

- `ft_linear_transform()`: 회전 부분의 곱에 `mat.trans`를 더한다.
- `ft_linear_transform_rotate()`: 회전 부분만 곱하고 이동은 더하지 않는다.

이 차이가 바로 점과 방향의 차이를 떠올리는 연결고리다. 다만 옛 함수의 이름이 수학적으로 엄밀한 분류를 보장하는 것은 아니다. 이동까지 포함하는 변환은 엄밀히는 아핀 변환이고, 순수 선형 변환과 구별된다.

## 6. 왜 마지막 열이 카메라 위치인가?

카메라 자신의 원점은 카메라 좌표에서 `(0, 0, 0)`이다. 이를 점으로 변환하므로 끝에 1을 붙인다.

```text
[ r00 r01 r02 tx ]   [ 0 ]   [ tx ]
[ r10 r11 r12 ty ] × [ 0 ] = [ ty ]
[ r20 r21 r22 tz ]   [ 0 ]   [ tz ]
[   0   0   0  1 ]   [ 1 ]   [  1 ]
```

회전 부분에는 전부 0이 곱해진다. 마지막 열만 남는다.

따라서 **camera-to-world 행렬의 마지막 열 위쪽 세 값은 카메라 원점의 월드 위치**다.

Python에서는 JSON의 행렬이 ‘행 목록’으로 읽힌다.

```python
matrix = frame['transform_matrix']
x = matrix[0][3]
y = matrix[1][3]
z = matrix[2][3]
```

- 첫 번째 대괄호: 몇 번째 행인지 선택.
- 두 번째 대괄호: 그 행의 몇 번째 값인지 선택.
- 인덱스는 0부터 시작하므로 `[0][3]`은 첫 행의 네 번째 값.

위 코드는 설명용이며 아직 도구에 추가하지 않았다.

### 실제 첫 프레임

파일: `data/demo-day-latest/capture/transforms.json`

좌표계 선언:

```text

```

첫 프레임 행렬을 읽기 편하게 반올림하면:

```text
[  0.673950   0.243095   0.697637  -0.702800 ]
[ -0.724376   0.031897   0.688667   0.168013 ]
[  0.145159  -0.969478   0.197589   0.582896 ]

```

원래 값에서 읽은 카메라 위치:

```text

```

원본 행렬에 `[0, 0, 0, 1]`을 곱해 실행한 결과:


이 계산은 ‘위치 추출 방법이 맞다’는 기계적 확인이다. ARKit이 실제 카메라 위치를 오차 없이 측정했다는 검증은 아니다.

## 7. 반대 변환: world-to-camera

두 변환은 방향이 반대다.

```text
camera-to-world: p_world  = R × p_camera + t
world-to-camera: p_camera = Rᵀ × (p_world - t)
```

왜 반대 순서일까?

1. 먼저 더했던 카메라 위치 `t`를 뺀다.
2. 그다음 회전을 되돌린다.

유효한 회전 행렬에서는 역행렬이 전치행렬과 같다. `Rᵀ`는 행과 열을 바꾼 행렬이다. 임의의 3×3 행렬에서 항상 성립하는 성질은 아니다.

world-to-camera를 4×4로 쓰면:

```text
[ Rᵀ  -Rᵀt ]
[ 0      1  ]
```

그래서 world-to-camera 행렬의 마지막 열은 일반적으로 카메라의 월드 위치가 아니다. 마지막 열의 이동 성분을 `u`라고 하면 카메라 위치는 `-Rᵀ × u`로 구한다. 여기서 `R`은 그 world-to-camera 행렬의 회전 부분이다.

실제 첫 프레임의 c2w를 강체 변환 공식으로 뒤집어 계산한 이동 성분은 약 다음과 같았다.

```text
[0.51074397, 0.73059274, 0.25941986]
```

이 값이 앞의 카메라 위치와 다른 것은 모순이 아니다. **변환 방향이 다르기 때문**이다.

원본 회전의 `RᵀR`과 단위행렬 차이의 최대 절댓값은 실행 결과 약 `4.09e-08`이었다. 이 예에서는 회전의 직교성이 수치적으로 잘 유지된다. 모든 프레임을 검사했다는 뜻은 아니다.

## 8. OpenGL의 앞 방향과 miniRT의 화면

확인한 miniRT의 `ft_screen()`에는 다음 코드가 있다.

```c
screen.z = -1;
```

화면을 카메라의 음의 z 쪽에 놓은 것이다. 현재 JSON도 OpenGL 카메라 좌표 관례를 선언한다. 이 관례에서 카메라는 로컬 `-Z` 쪽을 본다.

표준적인 열벡터 c2w 행렬에서는:

- 첫 번째 열: 카메라의 로컬 +X 축이 월드에서 향하는 방향.
- 두 번째 열: 로컬 +Y 축의 월드 방향.
- 세 번째 열: 로컬 +Z 축의 월드 방향.
- 따라서 실제 전방은 세 번째 열의 음수.

실제 첫 프레임으로 실행한 전방 방향은:

```text
[-0.69763672, -0.68866658, -0.19758892]
```

카메라 기준 전방의 점 `[0, 0, -1, 1]`을 월드로 변환한 결과는:

```text
[-1.40043640, -0.52065323, 0.38530725, 1.0]
```

점에는 카메라 위치가 더해지고 방향에는 더해지지 않는 차이를 여기서도 볼 수 있다.

주의: 이 선언만 보고 JPEG를 무조건 회전시키거나 축을 뒤집으면 안 된다. 저장된 센서 이미지, `image_orientation`, 내부 파라미터와 변환을 함께 확인해야 한다. OpenCV·COLMAP 관례로 바꿀 때도 카메라 로컬 축 변경과 월드 좌표 변경을 구분해야 한다. 지금은 변환을 추가하지 않는다.

## 9. 옛 miniRT 코드를 그대로 복사하면 안 되는 이유

`matrix.c`의 `ft_getmat_c2w()`는 `right`, `up`, `forward`를 만들고 `ft_mat_set(right, up, forward, cam->origin)`으로 저장한다.

한편 같은 파일의 `ft_linear_transform()`은 다음처럼 곱한다.

```c
rtn.x = mat.x.x * vec.x + mat.x.y * vec.y + mat.x.z * vec.z + mat.trans.x;
```

이 식에서 `mat.x`는 출력 x를 계산하는 한 행처럼 쓰인다. 하지만 `right`, `up`, `forward`라는 기저 벡터는 이 문서의 표준 열벡터 c2w 표현에서는 열에 들어간다.

따라서 이름만 보고 “옛 `mat.x`가 새 행렬의 첫 번째 열이다”라고 단정할 수 없다. 기저를 만드는 외적 순서와 실제 곱셈을 함께 추적하고, 알려진 회전 예제로 확인해야 한다. 이번 문서는 옛 회전 구현의 정확성이나 전체 관례 일치를 판정하지 않는다.

확실한 연결은 다음 두 가지다.

1. 옛 코드도 `trans`를 광선의 시작점으로 사용했다.
2. 점 변환에는 이동을 더하고, 방향 계산에서는 이동을 제거했다.

현재 ARKit 행렬은 현재 파일의 명시된 c2w 관례에 따라 읽는다. 옛 구조체의 메모리 배치와 현재 JSON의 행·열은 별개의 문제다.

## 10. miniRT와 현재 3D 복원의 연결

miniRT에서 주로 하던 일:

```text
카메라 + 알고 있는 물체
→ 픽셀마다 광선 생성
→ 물체와 교차 검사
→ 색을 계산해서 이미지 생성
```

지금 하려는 일:

```text
촬영 이미지 + ARKit 카메라 정보
→ 여러 사진에서 같은 점 찾기
→ 카메라에서 뻗는 광선들의 관계로 3D 점 추정
→ 카메라·기하 보정
→ 3DGS 학습으로 새로운 시점의 이미지 생성
```

miniRT는 장면을 알고 이미지를 만든다. 지금의 복원은 이미지를 관측해서 장면을 추정한다. 모든 과정이 단순히 렌더링을 역으로 실행하는 것은 아니지만, 카메라·좌표 변환·광선이라는 기반 개념은 연결된다.

이후 필요한 개념은 해당 구현 직전에만 공부한다.

| 다음 작업 | 그때 필요한 원리 |
|---|---|
| 카메라 위치 출력 | c2w의 마지막 열 — 이번 문서의 핵심 |
| 두 촬영 위치 사이 거리 | 좌표 차이와 벡터 길이 |
| 시선 방향 비교 | 방향 벡터, 내적과 각도 |
| 3D 점을 사진 위에 표시 | w2c, 핀홀 투영, 카메라 내부 파라미터 |
| 두 사진으로 점 추정 | 대응점, 광선, 삼각측량 |
| 카메라 보정 | 재투영 오차와 최적화 |

## 11. 직접 계산해 보고 싶을 때

작업 디렉터리는 현재 `arkit-sequential-sfm` 워크스페이스 루트다. 아래 명령은 파일을 읽고 계산만 한다. 코드 파일이나 원본 데이터는 변경하지 않는다.

```powershell
uv run python -c "import json,numpy as np; from pathlib import Path; d=json.loads(Path('data/demo-day-latest/capture/transforms.json').read_text()); T=np.array(d['frames'][0]['transform_matrix']); print('last column:',T[:3,3]); print('camera origin in world:',T@np.array([0,0,0,1])); print('forward direction:',T@np.array([0,0,-1,0]))"
```

이 명령은 계산 확인을 위한 참고다. 지금 바로 NumPy 슬라이싱까지 외울 필요는 없다. 실제 첫 구현에서는 읽기 쉬운 `matrix[0][3]`, `matrix[1][3]`, `matrix[2][3]`으로 시작할 수 있다.

## 12. 이번에 기억할 세 문장

1. 같은 점도 어느 좌표계에서 표현하느냐에 따라 숫자가 달라진다.
2. 점은 회전과 이동의 영향을 받고, 방향은 이동의 영향을 받지 않는다.
3. camera-to-world 행렬은 카메라 원점을 월드의 카메라 위치로 보내므로, 마지막 열에서 그 위치를 읽을 수 있다.
